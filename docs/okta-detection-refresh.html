Okta System Log and this lab

Quick refresher on what Okta emits, how the five rules map to it, and what was added to the repo for regression tests.

1. What is the Okta System Log?

Okta records administrative and user activity as events. Each event is a JSON object you pull via /api/v1/logs or export to a SIEM. Important fields you will see everywhere in this project:

  • eventType: the verb (for example user.session.start, user.mfa.factor.activate).
  • published: ISO timestamp (UTC). Rules use this for sliding windows.
  • outcome.result: often SUCCESS or FAILURE (logins, MFA, and so on).
  • actor: who caused the event (user id and alternateId email).
  • client.ipAddress and client.geographicalContext: source IP and geo (used for travel and country checks).
  • target: sometimes present (privilege grant target user, MFA factor row).

In a real SOC, you would normalize these into your SIEM schema. Here we read the native-ish shape from sample_events.json.

2. The five detections (mental model)

Rule Okta signals Idea in one line
MFA Fatigue system.push.send_factor_verify_push storm, then user.authentication.auth_via_mfa Someone spammed push prompts until the user approved.
Impossible Travel Two successful user.session.start with geo far apart in a short time Two logins too far apart for human travel (watch VPN FPs).
Brute Force Many failed user.session.start from one IP in five minutes Password guessing from a single source.
Suspicious MFA Enrollment Successful login from an "unusual" country, then user.mfa.factor.activate within ten minutes Attacker adds their factor after takeover (demo uses non-US login as unusual).
Admin escalation (after hours) user.account.privilege.grant outside 07:00 to 19:00 UTC Off-cycle admin grants deserve a ticket or confirmation.

3. What changed in the repo (tests and packaging)

New: requirements.txt lists requests (CLI and enrichment) and pytest.

New: tests/test_detections.py runs three kinds of checks:

  • Scenario slices: for each rule, only the UUID rows that belong to that attack are loaded. The rule must produce at least one alert with the expected rule_name.
  • Benign negative: only evt-benign-001 and evt-benign-002 must produce zero alerts from every detector (noise control).
  • Full sample: loading all events from sample_events.json must yield exactly one alert per rule (five rules, five alerts total when run per function).

New: .gitignore ignores .venv/ and pytest cache so local runs stay clean.

New: docs/pytest_last_run.txt holds an example pytest -v transcript. Re-run python -m pytest tests/ -v after any rule change and update it if you want the doc to stay in sync.

README: setup now uses a venv, documents the verification section, and links to this HTML page.

4. How sample_events.json is organized

Objects with _comment and _teach are teaching markers and are not events (they have no eventType, so the CLI skips them). Each real row has a uuid such as evt-mfa-001 so tests can select rows without fragile line numbers.

5. Commands to run locally

cd okta-detection-engine
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -m pytest tests/ -v
python okta_detector.py --input sample_events.json
